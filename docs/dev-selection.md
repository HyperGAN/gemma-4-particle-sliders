# Prospective DEV selection

The [selection plan](../research/dev-selection-v1.json) is fixed before model DEV inference. It declares 22 conditions: true unadapted OFF, three behavioral prompt controls, and 18 learned candidates from two recipes, steps 256/512/1024, and strengths .5/1/1.5. Step 1 qualifies engineering only. Learned conditions share one exact admitted TRAIN cache, seed 0, raw weights, batch 2, and the unchanged 1024-step recipe horizon.

Every condition reports all 42 supplementary DEV tasks and all 13 original Requests DEV tasks. All 42 supplementary environments pass negative/reference controls. Five original environments qualify; eight reference failures remain in the denominator and are annotated by the [environment receipt](../reports/original-dev-environment-qualification-v1.json). Immutable Docker image IDs prevent a moved tag from changing the comparison. The five original calibrated tasks provide a non-regression floor.

The runner fixes the common finalization prompt, tools-v2 instructions, official compaction, sampling, and 60-minute/100-counted-tool/500-turn budget. Command timeout is 300 seconds. Reported tool proposals include free official tools and can exceed the counted budget. Controls and candidates use the same LoRA-enabled engine settings; OFF loads no adapter weights. Each request and returned model alias is captured, and every patch receives fresh-container tests. Agent errors and incomplete captures remain reported. An agent error with an empty returned patch is unresolved, matching official evaluation; raw fresh-test results are also retained.

Selection requires the complete declared grid, or an actual model-preflight error receipt for an unqualified learned condition. Ranking uses resolved count, agent errors, emitted tool proposals, agent seconds, update count, strength, then recipe name. Promotion requires a strict improvement over OFF in the first three ranking fields and no regression on the five calibrated original tasks. Elapsed time alone cannot establish improvement. Prompt controls are reported comparators. Paired wins/losses, Wilson intervals, an exact discordance test, and per-repository counts expose the limits of the small panel.

`run_dev_controls.py` runs the four complete unadapted conditions. `run_dev_condition.py` runs one full condition and binds its implementation, actual server, request journals, patches, and verification receipts. `compare_dev_conditions.py` reaudits the complete grid offline before writing an immutable learned choice. Internal consistency checks do not authenticate invented JSON as model execution.

The [learned dispatcher](learned-dev-dispatch.md) waits for the actual complete baseline and measured conversions, then runs all eighteen learned conditions using that same frozen executor. Its strict GPU 0 contract preserves the current comparison while the separate resource proposal remains inactive.

The first actual task exposed a [receipt-audit schema defect](../reports/dev-schema-audit-recovery-v1.json) after fresh verification. Its unresolved result is retained. The corrected audit validates each stage's distinct schema and requires every other copied field to match. Recovery accepts only the entire complete contiguous prefix, with the same condition, packet, plan, generation code, and fresh-verification code; it performs no repeated model inference. The declared comparison remains unchanged.

The 49-task confirmation set stays locked until that choice. It supplies no targets, conversion activations, or selection feedback. The selected learned candidate and matched OFF are then evaluated once. Only an official learned submission exceeding a freshly verified public leader can satisfy the competition goal. There are currently no model DEV scores or pretrained optimizer updates.

The [confirmation access gate](confirmation-access.md) reaudits the actual completed choice through the unchanged baseline comparator and checks the selected model bytes before parsing that panel. Its preparation neither releases the current unfinished run nor performs confirmation inference.

The [training continuation](full-training-continuation.md) preserves the one-update engineering pilot and resumes its full game state through the declared checkpoints before starting the second recipe on the same cache.
